## 补核：前端实现实况 + React 评估（Alex 问「前端是什么代码，React 会不会更好」）

**前端实现（已核对代码）**
- 原生 ES Module，**零框架 / 零构建 / 零类型**；浏览器直接 `type="module"` 加载，
  `express.static` 直出，**没有打包步骤**
- 入口 `public/js/app.js`（2.3 KB）手写 hash 路由，`if/else` 分发 6 个 `renderXxxPage(root)`
- 每页 = 一个文件 + 一个渲染函数，**整页 `innerHTML` 字符串模板重建**（每页 4–10 处）
- 事件手动 `addEventListener`（每页 7–25 处），**每次重渲染后重新绑定**
- `store.js` 仅 464 B（极简 set/on/emit，全局只有 accounts + loading，**基本没用起来**）
- `api.js` 831 B（fetch 包装 + ApiError，消费 `{ ok, data }` 契约）；组件只有 `toast.js` 305 B
- 第三方只有 vendored 的 marked（40 KB）+ dompurify（122 KB），**无 CDN**
- 体积：自有前端 **244 KB** = JS 157 KB + CSS 90 KB + HTML 2.2 KB
- `app.css`：5294 行 / 877 选择器 / 16 媒体查询 / 2 keyframes

**新发现（已补进 as-built §4 第 12-13 条）**
- ⚠️ **主题系统漂移**：`设计规范-v2.0.md` §4 声明 **5 套主题**（framer/glass/fluent/bento/retro），
  实际 `app.css` 里 `data-theme` 只出现 4 次且**只有 fluent 有规则**，`index.html` 只有 **2 个按钮**
  → 3 套主题是纸面的
- **整页重建是规范写明的设计决策，不是技术债**：设计规范 §5 原文要求
  「事件绑定用『重建后重新 querySelectorAll 绑定』模式」→ 要改就得改规范，不是"缺框架"
  （附带不一致：规范写"JS IIFE"，实际是 ES Module）

**React 评估结论（Push back，已给用户）**
- 视觉像素由 CSS 决定 → 换框架**零视觉提升**；90 KB CSS 不动，像素级结果完全一样
- React 会改善：组件复用 / 状态↔视图同步 / 前端测试工具链 / 多人协作
- React 改善不了：数据模型缺完播字段、唯一约束锁死发布结构、6 页无复用压力
- 成本：引入构建链（node_modules 从 6 个直接依赖膨胀）、Docker 多阶段构建、
  **推翻 AGENTS.md §2 技术栈铁律**、**对面机器的 AI 上下文作废**、前端测试从零建、6 页重写
- 判断：前端选型**不是这个项目的瓶颈**；这与「README 5 个模块标待开发」是同一模式——
  **用确定性高的技术工作，替换确定性低的业务判断**
- 替代方案：局部 DOM 更新（只换变化那块，约 20 行）；或把 content-plan.js（30 KB / 30+ 函数）
  按职责拆 3-4 个原生 ESM 模块
