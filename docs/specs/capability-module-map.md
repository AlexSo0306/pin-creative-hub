# 能力栈 ↔ 工作台模块 · 映射

> 建立时间：2026-09-21 · 最后更新：2026-09-21（业务规则变更：一菜三发 → **一菜一发**；发布版本：**只发正片**）
> 输入 A：`拼好家创作运营中心/artifacts/项目功能蓝图.md`（运营工作区的 A–F 六层能力栈）
> 输入 B：`docs/specs/as-built-2026-09-21.md`（工作台 pin-creative-hub 六模块的现状基线）
> 目的：回答一个问题——**我的六层运营能力里，工作台到底托住了哪几层？**

---

## 0 · 一句话结论

**这两个东西不是同一根轴。**

- **蓝图**按「**能力**」组织：诊断 → 对标 → 拆解 → 改造 → 验证
- **工作台**按「**东西的状态**」组织：选题池 → 脚本库 → 制作中 → 已发布 → 已复盘

所以映射不上不是"模块不够多"，而是**工作台缺了「方法」这一维**——
它管得住"这条片子走到哪一步了"，管不住"我这次用的方法对不对"。

---

## 1 · 两条轴

| | 蓝图（能力栈） | 工作台（内容流水线） |
|---|---|---|
| 组织轴 | 运营**方法** | 内容**状态** |
| 单位 | 一层能力 | 一条内容卡 |
| 单元 | A 数据诊断 / B 对标研究 / C 内容拆解 / D 改造执行 / E 验证闭环（+ F 工具底座） | 今日工作台 / 灵感雷达 / 内容计划 / 数据复盘 / 账号矩阵 / 知识资产 |
| 时间性 | 可复用（方法沉淀后反复用） | 一次性（每条内容走一遍就结束） |

**关键差异**：蓝图里 A→B→C→D→E 是一条**方法链**；工作台里六个模块是一条**物件链**。
物件链跑完，方法不会自动沉淀。

## 3 · 最要紧的一处：A 的缺口和 E 的缺口是**同一件事**

```
A 缺完播字段  →  漏斗第二环算不出来  →  你不知道"开头到底行不行"
E 缺实验结构  →  没有"假设→样本→判定"的载体  →  你没法证明"改版有没有效"
                                          ↓
                        发现问题的地方 和 验证修复的地方，同时不存在
```

这不是两个独立的功能缺失，而是**同一条链的两端同时断了**。而这条链正是你当前最大的问题所在：
`5s 完播 27%`（健康线 >60%）、均播 6.6s、90% 的人看不到成片——**卡点在这一环，而工作台在这一环上什么都没有。**

## 4 · 已有的两条好链路（别动）

| 链路 | 实现 | 价值 |
|---|---|---|
| **灵感雷达 → 内容计划** | 对标作品可启发选题 | 方向对，但中间缺"可抄动作"的结构化字段 |
| **数据复盘 → 知识资产** | `knowledge_assets` 有 `source_review_id` + 唯一索引，**幂等生成一份草稿**（有测试覆盖） | 这是全库**唯一**把"做过的复盘"变成"可复用资产"的机制。设计得好，应作为其他链路的模板 |

**注意**：`知识资产 → 内容计划` 现在只是"引用"，**没有形成"下次按方法做"的约束**。所以方法沉淀了，但下次不一定用。

## 5 · 建议补的三处（按性价比排序）

> 原第 3 条「内容计划加版本维度」**已撤销**——业务规则改为一菜一发后，唯一约束与规则一致，无需改动。见 §7。

| # | 补什么 | 解决 | 成本 | 备注 |
|---|---|---|---|---|
| **1** | **给 `content_performance` 加完播字段**（`completion_5s_rate` / `avg_watch_duration`） | A 的缺口 | S（加列 + 迁移 + 表单 + 派生指标） | **最小改动、最大收益**。加完当天，漏斗第二环就能算了 |
| **2** | **新增「验证/实验」实体**：假设 + 样本量 + 观察指标 + 判定阈值 + 结论 | E 的缺口 | M–L（新表 + API + 页面） | 工作台最该加的一个模块。把"连发 5–7 条看 5s 完播破 50%"变成一条可跟踪的记录。**一菜一发让它的价值更高**，见 §6 |
| **3** | **灵感雷达加「可抄动作」强制字段**，并把拆解结论落进知识资产 | B 的缺口 | S–M | 不加的话，137 条对标会变成收藏夹坟场 |

**C（内容拆解）不建议进工作台**——它天然属于"桌面 + 脚本"（抽帧、逐帧读图），
工作台能做的只是**承接结论**（六拍模板作为知识资产的一条），不需要为它建模块。

## 6 · 一菜一发对验证闭环的**正面影响**（新增）

一菜三发时期，同菜多版本互相干扰：汉堡批次 B 的播放呈 **7,504 → 5,044 → 2,404** 的稀释。

改为**一菜一发**后：

- ✅ **一条内容 = 一个变量**，5s 完播的变化可以干净归因，不再被"同画面重复曝光"污染
- ✅ 「连发 5–7 条看 5s 完播破 50%」这个实验**第一次变得可执行**——因为样本之间不再互相稀释
- ⚠️ **代价**：版本间对比消失。以前能拿同一条菜比较正片 vs 快剪，现在只能跨菜比较（噪声更大）

→ **结论：一菜一发让「验证实体」（建议 2）从"值得做"变成"应该马上做"**，因为它解决了实验的前提条件。

### 随之而来的一个决策：发哪个版本？

数据给出的三个版本强项不同（来自 `0904抖音数据诊断报告.md`）：

| 版本 | 强项 | 实测 |
|---|---|---|
| **正片** | 涨粉 + 播放量 | 单条均增粉 12.3、贡献 57% 涨粉、播放均值 8,062（最高） |
| **情侣快剪** | 主页访问 | 1.06%，是其他版本的 1.7–2 倍 |
| 开头快剪（纯享 4–8s） | 三项垫底 | 已建议砍掉或改造 |

**推荐发正片**，理由：
1. 播放均值与涨粉贡献都最高
2. **主页 → 关注 19.2% 已经是健康线 2 倍**，说明转化层健康——引流不是瓶颈，快剪的强项用不上
3. 瓶颈在**留存**（5s 完播），而正片有完整的开头改造空间（6 秒微预告六拍结构就是从这个版本提炼的）

→ 这条建议可直接作为建议 2 里**第一个实验的假设**。

### ✅ 决策已落定（2026-09-21 · 用户确认）

> 用户原话：「以后全部都是发真片」——按「**正片**」理解（同音笔误）。

→ **快剪 / 纯享两个版本停做，只发正片。** 上表的三版本对比从此只作历史参考。
→ 连带效果：**「版本」不再成为内容计划的维度**，与一菜一发（`UNIQUE(content_card_id, platform)`）完全对齐 —— 一个内容卡 = 一个版本 = 每平台一条发布记录。
→ 可执行化：把它当作建议 2 的**第一个实验假设** —— 以「正片 + 6 秒微预告六拍开头」为实验版本，观察 5s 完播是否破 50%。

## 8 · 与 React 迁移的优先级关系（直说）

按本次映射，工作台的功能缺口排序是：

```
1. 完播字段（A）          ← 不修，漏斗第二环永远是黑的
2. 验证实体（E）          ← 不建，改版效果永远无法证明（一菜一发后更该做）
3. 可抄动作（B）          ← 不修，对标库继续囤积
4. React 迁移             ← 换的是"怎么盖"，上面 3 条换的是"盖什么"
```

React 迁移是**架构层**的工作，上面 3 条是**产品层**的工作。两者不冲突，但有一个现实约束：
**迁移期间前端处于双轨状态，此时加新模块会让双轨期变长、冲突变多。**

→ **建议顺序**：先做完播字段（S 级，一两天，纯数据层改动，迁移前后都不浪费）→
再决定是「先迁移再建验证实体」还是「先建验证实体再迁移」。
