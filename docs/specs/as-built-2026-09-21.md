## 4 · 未写进任何 spec 的事实（代码里存在、文档里没有）

> 这一节是本次梳理**最有价值的部分**——这些事实只存在于代码里，下一个接手的人（或另一台机器的 AI）会踩。

1. **统一 API 响应契约**  
   `src/app.js` 注入中间件：成功补 `{ ok: true, data }`，失败补 `{ ok: false, error }`。  
   所有前端调用依赖此包装。**`AGENTS.md` 与 6 份 Feature Spec 均未记录。**
2. **前端是 hash 路由单页，且路由名与文件名不一致**  
   `public/index.html` 用 `data-route` + `#/xxx`。映射关系：
   | 路由               | 页面文件                             |
   | ---------------- | -------------------------------- |
   | `#/dashboard`    | `pages/dashboard.js`             |
   | `#/inspiration`  | `pages/inspiration.js`           |
   | `#/content-plan` | `pages/content-plan.js`          |
   | `#/review`       | **`pages/data-review.js`** ← 不一致 |
   | `#/accounts`     | `pages/accounts.js`              |
   | `#/knowledge`    | `pages/knowledge.js`             |
3. **13 个 API 挂载点，其中一处是二级挂载且顺序敏感**  
   `/api/dashboard` 与 `/api/dashboard/monitor` 是两个独立 router，**monitor 必须在 dashboard 之后注册**，否则被吞。
4. **SPA 兜底用 Express 5 的通配符写法**  
   `app.get('*path', …)` —— 不是 Express 4 的 `'*'`。改动路由时容易踩。
5. **`dashboard_todo_actions` 是日粒度状态，不是任务实体**  
   唯一约束 `(workspace_id, todo_key, effective_date)`。「今日待办」的完成/推迟是**当天有效**，不是持久任务列表。文档未描述此语义。
6. **`content_publish_records` 的唯一约束 = 业务规则，不是缺陷**  
   `UNIQUE(content_card_id, platform)` → **一个内容卡在同一平台只能有 1 条发布记录**。  
   ✅ 业务规则为**一菜一发**（2026-09-21 确认），该约束与之**完全一致**，是正确设计。  
   ✅ 发布版本亦已确认：**只发正片**（2026-09-21，用户原话「以后全部都是发真片」），快剪 / 纯享停做。
   → 一个内容卡 = 一个版本 = 每平台一条发布记录，约束与业务**双向对齐**。详见 `capability-module-map.md` §6。  
   ⚠️ 此前记为"限死发布结构"属**过度推断**——全库检索证实「一菜三发 / 快剪 / 纯享」
   在 `pin-creative-hub` 内**零命中**（只存在于 `handoff.md` 等业务侧文档），
   即工作台从未声明要支持一菜三发。教训：不要把业务侧的做法当成产品需求。
7. **`content_performance` 没有任何完播类字段**  
   现有：`plays / likes / comments / bookmarks / shares / followers_gained / leads / record_date`。  
   **无 5s 完播率、无均播时长、无完播率** → 现有模型无法承载留存类诊断。
8. **迁移脚本入口**  
   `npm run migrate:inspiration` → `src/migrate-inspiration.js`（仅此一个迁移命令）。
9. **`inspiration_settings` 有三个热点倍数阈值**  
   `hot_likes_multiplier` / `hot_plays_multiplier` / `hot_visible_multiplier`，默认均 2.0。监控"爆款"的判定口径由它决定。
10. **`src/routes/inspiration.js` 单文件导出 5 个 router**  
    `creators` / `posts` / `monitor` / `settings` / `sync`，35 KB，是全库最重的路由文件。  
    5 个 router 挤在一个文件里 → 这是两机分工最容易撞车的位置（`AGENTS.md` §5.2 的"按模块切"在这里失效）。

11. **前端实现方式：原生 ES Module，零框架、零构建、零类型**
    - 浏览器直接加载 `type="module"`，**没有打包步骤**，`express.static` 直出
    - 入口 `public/js/app.js`（2.3 KB）手写 hash 路由，`if/else` 分发到 6 个 `renderXxxPage(root)`
    - **每页 = 一个文件 + 一个渲染函数**，整页用 `innerHTML` 字符串模板重建（每页 4–10 处）
    - 事件：手动 `addEventListener`（每页 7–25 处），**每次重渲染后重新绑定**
    - 状态：`public/js/store.js` 仅 464 字节，极简发布订阅（`set/on/emit`），全局只有 `accounts` + `loading`，**基本未使用**
    - API：`public/js/api.js` 831 字节，一个 `fetch` 包装 + `ApiError` 类，消费 §4.1 的 `{ ok, data }` 契约
    - 组件：只有一个 `toast.js`（305 字节）
    - 第三方：仅 vendored 的 `marked`（40 KB）+ `dompurify`（122 KB），**无 CDN 依赖**
    - 体积：自有前端 **244 KB**（JS 157 KB + CSS 90 KB + HTML 2.2 KB）；`app.css` 5294 行 / 877 个选择器 / 16 个媒体查询

12. **⚠️ 主题系统：设计规范声明 5 套，实际实现 2 套**（本次新发现的漂移）
    - `docs/specs/设计规范-v2.0.md` §4 列 5 套：`framer` / `glass` / `fluent` / `bento` / `retro`
    - `app.css` 中 `data-theme` 仅出现 **4 次**，且**只有 `fluent` 有覆盖规则**；`glass` / `bento` / `retro` **零 CSS**
    - `index.html` 只有 **2 个**主题按钮：`framer`（深色）/ `fluent`（浅色）
    - → 规范里的"5 套主题系统"有 3 套是纸面的

13. **整页重建是「规范写明的设计决策」，不是技术债**
    `docs/specs/设计规范-v2.0.md` §5 原文规定：「一切可变数据集中在 JS IIFE 顶部…渲染函数读 state 生成 DOM；
    事件绑定用**「重建后重新 querySelectorAll 绑定」**模式」。
    即当前 `innerHTML` 整页重建 + 重新绑定，是**规范明确要求**的做法。
    → 若要改成局部更新，**要改的是规范，不是"缺个框架"**。
    （附带一处不一致：规范写"JS IIFE"，实际代码是 ES Module + `export function`。）

14. **移动端适配已大量完成（不是"未来要兼容"，是"已经做了大半"）**
    - `index.html` 已有 `viewport`（`width=device-width, initial-scale=1`）+ `theme-color` meta
    - `app.css` **4 档断点**：1180px / 1120px / 860px / 640px，共 16 个媒体查询，
      其中 `≤640px` 有 **5 个独立 block** 逐页细调（dashboard / data-review / inspiration / knowledge / content-plan）
    - `≤860px`：`.app-shell` 转单列，侧边栏折叠为顶部横条（`sticky` + 横向 grid）
    - `≤640px` 具体行为：内容看板转**横向滚动 + `scroll-snap-type: x proximity`**（`repeat(5, min(82vw,286px))`）；
      抽屉全屏化（`width:100%; border-left:0`）；日历格缩到 52px 并隐藏小字；
      指标卡转两列并去掉内部边框；表单按钮全宽；图表区可横向滚动
    - 仓库根目录有 4 张移动端走查截图（`demo-mobile.png` / `demo-mobile-fixed.png` /
      `demo-glass-mobile.png` / `demo-color-mobile-final.png`）
    → **CSS 层面移动端已是一等公民**，这正是原生 CSS 单文件的好处：无 CSS-in-JS 运行时、无主题 Provider 包裹，媒体查询直接生效

15. **⚠️ 手机断点下导航被砍到 2 项，且无替代入口**（严重缺陷）
    `app.css` 的 `≤640px` 块中：`.main-nav a:nth-child(-n+4) { display: none; }`
    → 被隐藏的是 **「今日工作台 / 灵感雷达 / 内容计划 / 数据复盘」** 前四项
    → 全库无 `hamburger` / `bottom-nav` / `mobile-nav` / `menu-toggle` 任何替代机制
    → **手机上只剩「账号矩阵」「知识资产」两个入口**，恰是最不常用的两个

16. **⚠️ 内容计划的拖拽用 HTML5 DnD，触屏不可用**（结构性缺陷）
    `content-plan.js` 只有 `draggable` + `dragstart/dragover/dragleave/dragend`，
    **零 `pointerdown/pointermove/pointerup`、零 `touchstart/touchend`**
    → 五状态看板的推进依赖拖拽 → **该模块在手机上不可用**（iOS Safari 不触发 DnD）

17. **断点声明与实际不符**（新发现的漂移）
    `docs/specs/设计规范-v2.0.md` §2.3 声明 2 档断点：≤1100px、≤920px；
    实际 `app.css` 是 1180 / 1120 / 860 / 640。
    行为对上了（860px 确实把侧边栏折叠为顶部横条），但**数值不符**。
    另：`设计走查-计划.md` §3 预扫出 9 条候选偏差，**无一条是移动端的**（§G 响应式列为 P1 却未预扫出问题）；
    其 §5 开放问题还假设"glass / fluent / bento / retro 四套主题"存在（与第 12 条冲突）。

## 6 · 数据模型（16 张表，核对自 `src/schema.sql`）

| 分组       | 表                                                               |
| -------- | --------------------------------------------------------------- |
| 基础       | `schema_migrations`、`workspaces`                                |
| 自有账号     | `owned_accounts`、`owned_account_platforms`                      |
| 内容生产     | `content_cards`、`content_publish_records`、`content_performance` |
| 复盘与沉淀    | `review_conclusions`、`knowledge_assets`                         |

| 同步       | `inspiration_settings`、`inspiration_sync_runs`                  |

**软删除约定**：`owned_accounts` / `content_cards` / `knowledge_assets` 用 `deleted_at` 软删，且唯一索引带 `WHERE deleted_at IS NULL` 条件。**改唯一约束时必须同步这个条件**，否则软删记录会占位。

**多租户约定**：几乎所有表都带 `workspace_id`（对应"选题空间"的数据隔离框架）。
