# ADR-0001 · 前端迁移到 React

> 状态：**已接受（Accepted）** — 2026-09-21，决策人 Alex
> 记录人：白灵 🎬
> 影响范围：`public/` 全部前端代码、`AGENTS.md` §2 技术栈铁律、Docker 构建、两机 AI 协作流程
> 关联：`docs/specs/mobile-usability-v1.0.md`、`docs/plans/2026-09-21-react-migration.md`

## 1 · Context（决策背景）

工作台前端现状（详见 `docs/specs/as-built-2026-09-21.md` §4 第 11 条）：

- 原生 ES Module，**零框架、零构建、零类型**，浏览器直接加载
- 6 个页面，自有代码 244 KB（JS 157 KB + CSS 90 KB + HTML 2.2 KB）
- 每页 = 一个文件 + 一个 `renderXxxPage(root)` 函数，整页 `innerHTML` 字符串模板重建
- `store.js` 仅 464 B，基本未使用；组件只有 `toast.js` 一个

**触发事件**：Alex 提出「未来想要兼容移动端」。核查后发现三处缺陷（D1 手机导航被砍到 2 项 /
D2 看板拖拽触屏不可用 / D3 重建丢焦点）。

**决策**：迁移到 React。

## 3 · 记录在案的反面证据（Counter-evidence）

> 以下为决策前给出的分析结论，**完整保留**，供未来复盘。不因决策已下而删除。

1. **D1 与框架无关**：`.main-nav a:nth-child(-n+4) { display:none }` 是 CSS + 导航信息架构问题。
   且它**偏离了项目自己的规范**（`docs/specs/设计规范-v2.0.md` §2.3 原文要求"导航横向滚动"）。React 不解决它。
2. **D2 不需要 React**：Pointer Events 或 dnd-kit 都能解。React 的收益是 dnd-kit 现成，不是唯一解。
3. **6 页规模无复用压力**：最大页面 35 KB、每页一个渲染函数，心智负担低。
4. **手机端运行时开销**：React + ReactDOM min+gzip ≈ 45 KB，加客户端路由 ≈ 20 KB+。
   而当前方案是零运行时、无 hydration、依赖全 vendored（内网访问不受外网影响）。
5. **移动端 CSS 已做完大半**：4 档断点、16 个媒体查询、≤640px 有 5 个逐页 block。
   这部分工作在迁移中**基本要重做**。
6. **成本项**（见 §4）中，三项与"另一台机器"相关，会打断已建立的跨机协作机制。

**分歧点已澄清**：
> 上述 1–5 针对的是「**今天这三个缺陷是否需要 React**」——答案是不需要。
> 而本次决策针对的是「**中长期架构方向**」——在这个框架下，React 是可辩护的选择
> （页面会增长、可能要 PWA / 原生 App、组件复用与生态有长期价值）。
> **两个结论不冲突。** 本 ADR 记录的是后者。

## 5 · 决策的**回滚触发条件**（Reversal Triggers）

> 这是本 ADR 最重要的一节。**迁移不是不可逆的**，但需要预先约定"什么时候该回头"，
> 否则会陷入"已经投入这么多，不能停"的沉没成本陷阱。

以下任一条件成立，应**暂停迁移并重新评估**：

- [ ] **T1**：试点页（账号矩阵）迁移完成后，**代码行数没有下降**（说明组件化没带来收益）
- [ ] **T2**：试点页迁移耗时 **超过 2 个工作日**（说明成本被低估，全量迁移会失控）
- [ ] **T3**：迁移后手机端**首屏时间比原生版更慢**（运行时开销抵消了收益）
- [ ] **T4**：迁移过程中出现**需要改动 `src/` 后端**才能继续的情况（说明前端边界没划清）
- [ ] **T5**：两机协作**连续两周无法同步**（说明机制已被破坏）

触发任一条 → 回到本 ADR §2 的方案 A 或 B，把已完成部分作为"新架构验证"保留即可。
